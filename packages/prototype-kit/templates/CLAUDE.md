# {{DEMO_NAME}} — {{CLIENT_NAME}}

This folder is a **Prototyper demo**: a static website prototype shown to the client to agree on design and content. The client reviews it through a shared link where they can edit texts, replace images and leave notes. Their edits are applied back to these files **by key**, so the rules below are strict.

Content language: **{{LANGUAGE}}**. Write all visible copy in this language. Code, keys, file names and comments stay in English.

## Where things are

- `brief.md`: what the client wants. Read it first.
- `src/`: the site. One `.html` file per page, `src/assets/` for images, `src/styles.css` for Tailwind.
- `src/tokens.css`: brand tokens (colors, fonts, radii) as a Tailwind v4 `@theme`. Use these tokens, don't hard-code brand colors.
- `{{BRAND_DIR}}/BRAND.md`: brand guidelines, if present. Follow them.
- `references/`: screenshots the developer picked as inspiration, with notes in `references/notes.md`. Look at them with the Read tool.
- `.prototyper/`: managed by the app. Read files there when asked (for example feedback rounds). The only file you may write there is the `replies.json` of the round you are working on.

`dist/` is generated by the app. Never edit it.

## Tech rules

- Plain static HTML5, one complete document per page (`<!doctype html>`, `<html lang>`, `<head>`, `<body>`).
- Styling with **Tailwind CSS v4** utility classes. Each page links `styles.css` (the app compiles it). Put custom CSS in `src/styles.css` only when utilities can't do it.
- JavaScript only for small interactions (mobile menu, accordion, tabs, carousel), inline at the end of `<body>` or in `src/assets/site.js`. No frameworks, no build steps, no CDNs except Google Fonts.
- Internal links are relative: `href="services.html"`, `href="index.html#contact"`. Every page you link to must exist.
- Responsive from 360 px to 1440 px+. Mobile navigation must work.
- Accessible: semantic landmarks, one `<h1>` per page, heading order, `alt` on every image, visible focus, sufficient contrast.
- Forms are fake (no backend): `action="#"` and a small inline script that shows a thank-you message.

## The content contract (mandatory)

Every piece of visible, client-editable content carries a **`data-pt` key**. This is what lets the client edit it.

```html
<h1 data-pt="home.hero.title">Tax advice for business owners</h1>
<p data-pt="home.hero.lead" data-pt-type="rich">At your side for <b>20 years</b>.</p>
<img data-pt="home.hero.image" src="assets/ph-hero.svg" alt="Our team in the office">
<a data-pt="home.hero.cta" href="contact.html" class="btn">Book a call</a>
<a href="contact.html" class="btn"><span data-pt="home.cta.label">Contact us</span> <svg>…</svg></a>
<section data-pt-bg="home.quote.bg" style="background-image: url('assets/ph-quote.svg')">…</section>
```

Rules:

1. **Keys**: lowercase, dot-separated, at least two segments: `<page>.<section>.<item>`. Lists use an index: `services.items-1.title`, `services.items-2.title`. Shared header and footer content uses `global.`: `global.nav.services`, `global.footer.address`.
2. **One key means one piece of content.** The same key may appear on several pages only when the content is identical (header, footer). Different content needs a different key.
3. **Kinds**:
   - no `data-pt-type`: `<img>` is an image, `<a>` is a link (label + href), anything else is plain text;
   - `data-pt-type="rich"`: text with inline formatting, which may contain only `b`, `strong`, `i`, `em`, `a`, `br`;
   - `data-pt-bg="key"`: the element's inline `style` background image is editable; the URL must be in the `style` attribute.
4. **Plain-text and link elements contain only text.** If a link or button has an icon, put the key on a `<span>` holding the label, not on the `<a>`.
5. **No nesting.** An element with `data-pt` must not contain another element with `data-pt`. (`data-pt-bg` containers may contain keyed elements.)
6. **Explicit closing tags** on every keyed element.
7. Every `<img>` has a key. Purely decorative elements (icons, dividers, the © line) get `data-pt-ignore` and are then skipped entirely, including their children.
8. **Stable keys across versions.** When you revise a page, keep existing keys for content that still exists. Only add keys for new content and drop keys for removed content. Never rename a key just for style.

The app runs a linter after every change and will send you its errors. Fix all of them.

## Images

There are no real photos yet. Create SVG placeholders in `src/assets/`, named `ph-<what>.svg`, and use them like real images:

- size them to the intended aspect ratio (`viewBox`), with a neutral tone that fits the palette;
- add a short centered caption describing the ideal photo, in the content language (for example "Team photo in the office, natural light"), so the client knows what to upload;
- logos: if `{{BRAND_DIR}}` contains the client's logo, copy it into `src/assets/`; otherwise make a simple text-based SVG wordmark.

## Copy

Write realistic, specific copy based on the brief: no lorem ipsum, no "Lorem Company". Keep it plausible and modest; don't invent awards, figures or client names unless the brief gives them. Where a fact is unknown, write a believable placeholder and keep it easy to spot for the client (for example "[number of years]").

## When working on a revision

You will be given a feedback file from `.prototyper/rounds/<n>/`. The client's direct text and image edits **are already applied** to `src/`. Treat that copy as approved: don't rewrite it unless a note explicitly asks you to. Address every note, then write:

- `CHANGELOG.md`: prepend a `## v<n>` section with a short, client-friendly list of what changed;
- `.prototyper/rounds/<n>/replies.json`: `{ "<noteId>": { "status": "resolved" | "answered", "reply": "<short reply to the client, in the content language>" } }`. Use `answered` when you didn't change anything and explain why.
